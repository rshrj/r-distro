R-Distro

An independently built Debian derivative — rebuilt from source, signed, and owned end to end.

The tooling here pins Debian to an exact snapshot, rebuilds its ARM64 base from source, and publishes each pass as an immutable signed archive that the next pass builds against. The destination is a rolling system that tracks Debian testing continuously, carries local patches across each advance, and composes the result into images for a fleet.

What this is

Most Linux distributions are things you consume. R-Distro is an attempt to build one you own — where depending on Debian is a choice rather than a necessity.

  1. Own the tooling. Be able to rebuild Debian's base from source yourself, and know exactly which packages you still cannot. That measurement is the self-hosting boundary.
  2. Inject your own code. A defined point in the pipeline where local patches — or entirely your own versions of a source package — enter the build and travel with it across every subsequent update.
  3. Ship a distribution. Compose Debian, that tooling, and the custom code into installable artifacts — ultimately an ISO — for a managed fleet of machines.

The pinned snapshot is a stage, not the design. Advancing the pin — safely, repeatedly, carrying your patches with it — is the actual product.

Everything currently in the repository is scaffolding for that: the generational +rdistroN versioning, the campaign controller with durable state, the immutable signed releases. They exist so that advancing the snapshot becomes a routine operation rather than an event.

Background

The idea comes from gLinux, Google's in-house Linux distribution for workstations. Its current incarnation, Rodete — "Rolling Debian Testing" — replaced an Ubuntu LTS-based predecessor, and the argument for it, laid out in public DebConf talks, was that continuous small migrations beat big-bang ones. Rather than a painful distribution upgrade every two years, gLinux tracks Debian testing and moves forward in small, tested increments.

The machinery that does this is a pipeline that continuously ingests Debian, rebuilds it, rebases Google's local patches on top, gates on tests, and advances the tracked snapshot only when the result is good. R-Distro is that idea rebuilt from scratch at a scale one person can operate.

The differences are honest ones. Google rebuilds the whole archive because Google has the compute. R-Distro computes the minimum set that must be rebuilt for the claim to mean anything, and lets everything else fall through to Debian unchanged — a hybrid archive that works because +rdistroN sorts above Debian's own versions while preserving upstream ordering.

Roadmap

Every claim below was checked against the source rather than remembered. Where something is missing, the evidence for that is given too.

Shipped working today
  • Pinned reproducible build environmentDebian snapshot 20260813T165000Z and a digest-pinned bootstrap image, with Check-Valid-Until disabled so long campaigns don't expire mid-run.
  • Source rebuild with generational versioningapt-get source → +rdistroN → mk-build-deps → dpkg-buildpackage, unprivileged, inside a pinned container.
  • Package build policy as dataPer-package exceptions live in config/package-policy/<pkg>.env instead of being special-cased in the build script.
  • Signed APT archiveIndices generated with apt-ftparchive, Release clear-signed and detach-signed inside the build container.
  • Dependency closure analysisTwo independent implementations — one from observed build dependencies, one from declared metadata — so neither is trusted alone.
  • Deterministic self-hosting boundaryA fixed point, not a truncated walk: 4725 sources, 7570 binaries, 14 rounds, zero unresolved relations.
  • Durable campaign controllerSQLite job state, immutable numbered attempts, parallel workers, pause/resume, failure classification from build logs.
  • Validated immutable promotionvalidate → stage → promote, finishing with an atomic rename so a release is never half-published.
  • Per-build provenance measurementEvery build records how many of its dependencies came from R-Distro versus Debian. Self-hosting is the state where the Debian count reaches zero.
  • Distribution identityThree native packages of R-Distro's own: a dpkg vendor declaring Debian as parent, the archive keyring installed systems verify against, and a metapackage defining the minimum supported install. An installed machine reports R-Distro to dpkg-vendor and records the snapshot it descends from.
  • A source workspace for local changesEvery source has an origin derived from the filesystem — native, Debian plus overrides, or plain Debian. source-edit gives a git tree whose first commit is the pristine upstream state, and source-save writes the delta back as a quilt series. Not yet read by campaign builds; see Next.
Next the gap between a pinned rebuild and a rolling distribution
  • Parameterise the pinThe snapshot is hardcoded in all three Dockerfiles and the date is baked into image tags across seven tracked files. Meanwhile manifests/2026-08-13/bootstrap-snapshot.txt declares the pin as data and nothing reads it. Advancing the snapshot today means hand-editing about ten places.
  • Snapshot diff → changed-source manifestThe missing primitive, and the cheapest one: it is Sources index parsing, not compute. It feeds the existing rdistroctl plan --manifest unchanged, so the whole build path is reused.
  • Wire overrides into the buildPatches can be authored and saved to overrides/<source>/patches/, but nothing in the campaign path reads them: neither build-package.sh nor rdistroctl.py references the directory, so rdistroctl run rebuilds the unmodified source, succeeds, and reports nothing unusual. The hook to apply them at already exists — PRE_BUILD_COMMAND runs in the source tree after apt-get source and before the build.
  • Patch rebase detectionThe part that makes it a system rather than a pile of diffs: notice when a local patch stops applying or has landed upstream, and drop it.
  • Build the imageThe simple-cdd configuration, the profile and the pinned debian-installer manifest are in image/, with the installer's mirror preseeded to the same snapshot everything else builds against. No ISO has been produced from it yet.
Planned further out
  • Test gatingautopkgtest and sbuild are installed in the controller image but are not invoked by any script. Gating an advance on tests is what makes rolling safe.
  • Explicit hybrid-archive policyA declared split between packages R-Distro rebuilds and packages it deliberately passes through to Debian. This already works implicitly through version ordering; it should be a stated policy, not an accident.
  • Install from R-Distro's own archiveThe installer image currently preseeds Debian's pinned snapshot as its mirror. Pointing it at a promoted R-Distro release instead is what makes the ISO genuinely R-Distro's rather than Debian's with extra packages.

Scale

This runs on one laptop

All of it — every build, every campaign, the archive server and the analysis — runs on a single MacBook Pro M3 Pro. There is no build farm, no CI fleet, no object storage.

That constraint shapes the architecture rather than limiting the ambition. Rebuilding the entire Debian archive is not available; computing the minimum set that must be rebuilt, and rebuilding only what changed since the last snapshot, is. Both are better engineering than brute force, and both were forced by the constraint.

The numbers are real: the current campaign has consumed roughly 28 GB of build workspace and 9.6 GB of promoted releases. Disk is a genuine failure mode — the controller classifies disk as its own failure category.
